## Description

Lets admins keep the list of people who use the tool: add, edit, deactivate and reactivate, with email as the unique case-insensitive key and protection against removing the last active admin.

## Scope Detail

- Person list and add with name, email, role
- Edit name, role and (as a controlled admin-only edit) email
- Deactivate with warning showing how many future bookings will be cancelled; cascade through F-07.05
- Reactivate without restoring cancelled bookings
- Web and phone screens per the canvas

## Technical Approach

People service in the M-04 module with audit events PersonCreated, PersonUpdated, PersonDeactivated and PersonReactivated; UI built on F-03 components.

## Stories

---

### S-04.01.01: List and add people

**Estimated Hours:** TBD

As a Software Engineer, I want an admin people list and add form so that an admin can build the directory of up to about 50 people, so that every booking links to a real user.

_Acceptance criteria:_

- [ ] An admin can add a person with name, email and role (Employee or Admin); the person is active and appears in the list.
- [ ] Adding an email that already exists, ignoring case, is refused with a message naming the rule; email format is validated.
- [ ] When the directory would exceed 50 active people, the admin sees a message that the pilot is sized for about 50 (working assumption: warning, not a block).

_Notes:_ PI-01, PI-02, PI-03, NFR-001, NFR-023; audit PersonCreated.

---

### S-04.01.02: Edit a person

**Estimated Hours:** TBD

As a Software Engineer, I want to edit a person's name, role and email so that the directory stays correct as people change.

_Acceptance criteria:_

- [ ] An admin can change name and role; a person holds exactly one role.
- [ ] An email change is an admin-only controlled edit that re-checks uniqueness ignoring case; past bookings follow the person because they reference the id.
- [ ] Demoting the last active admin is refused with a message naming the last-admin rule.

_Notes:_ PI-07, PI-09; audit PersonUpdated with old and new values by id.

---

### S-04.01.03: Deactivate a person with a warning and cascade

**Estimated Hours:** TBD

As a Software Engineer, I want deactivation to warn how many future bookings will be cancelled and then cancel them so that leaving employees release their rooms.

_Acceptance criteria:_

- [ ] Before confirming, the admin sees the number of future Confirmed bookings that will be cancelled.
- [ ] On confirm the person becomes inactive, and their future bookings are cancelled as cancelled by admin (origin PersonDeactivated), never late-flagged; past and in-progress bookings are unchanged.
- [ ] Deactivating the last active admin is refused; the person no longer appears in the picker.

_Notes:_ ADR-0014 rule 3, PI-05, PI-06; uses F-07.05; E2E-012.

---

### S-04.01.04: Reactivate a person

**Estimated Hours:** TBD

As a Software Engineer, I want to reactivate a person so that someone who returns can use the tool again.

_Acceptance criteria:_

- [ ] An admin can reactivate an inactive person, who then reappears in the picker.
- [ ] Bookings cancelled at deactivation are not restored.
- [ ] Audit event PersonReactivated is recorded.

_Notes:_ M-04 capability 4.

---

### S-04.01.05: Build the people screens for web and phone

**Estimated Hours:** TBD

As a Software Engineer, I want the people screens from the design so that admins can manage people on desktop and phone.

_Acceptance criteria:_

- [ ] The web screen is table-first with a detail pane; the phone screen is a list with a detail view, following S03-people and S03-people-mobile.
- [ ] Deactivate and reactivate use the confirm modal (web) or sheet (phone); the last-admin block state shows the named rule.
- [ ] Inactive people are visibly marked and the screens meet the accessibility baseline.

_Notes:_ Admin-only (F-04.03).
