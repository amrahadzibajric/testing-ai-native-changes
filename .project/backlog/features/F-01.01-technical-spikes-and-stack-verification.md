## Description

Retires the technical unknowns the architecture explicitly asked the delivery team to verify at build start. The output is a short written finding per spike, not production code.

## Scope Detail

- SQLite immediate write transaction API, WAL mode and busy timeout with Microsoft.Data.Sqlite and EF Core
- Current .NET LTS version and package baseline
- Time zone data availability for Europe/Berlin on the demonstration machine, including offsets across both 2026/2027 DST transitions
- Feasibility of a 15-minute-snapped timeline board and a per-room phone list in server-rendered Razor Pages with a small amount of JavaScript
- Architecture baseline note confirming module structure and seams

## Technical Approach

Small throwaway console or test projects, each ending with a findings note that later features cite. Nothing from the spikes is merged as production code except configuration values.

## Stories

---

### S-01.01.01: Prove the SQLite immediate write transaction and concurrency behaviour

**Estimated Hours:** TBD

As a Software Engineer, I want to prove that an immediate write transaction with WAL mode and a busy timeout serialises competing writers so that the booking-write service can guarantee no double booking on SQLite.

_Acceptance criteria:_

- [ ] The exact Microsoft.Data.Sqlite / EF Core API for starting an immediate (write-lock-at-start) transaction is confirmed against current documentation and recorded.
- [ ] With 20 parallel requests for the same slot in the spike, exactly one succeeds and the others wait and then observe the conflict; none fails with a "database is locked" error.
- [ ] The recommended WAL and busy-timeout values are recorded for use by F-02.02 and F-06.02.

_Notes:_ Addresses the follow-up in ADR-0025 and the Open Question in arch v1.2. A deferred transaction is not acceptable because two requests could both read before either writes.

### S-01.01.02: Confirm the runtime and package baseline and time zone data

**Estimated Hours:** TBD

As a Software Engineer, I want to confirm the current .NET LTS, the EF Core SQLite package versions and the Europe/Berlin zone data so that the scaffold starts on a supported baseline and office-time rules are correct on the demonstration machine.

_Acceptance criteria:_

- [ ] The current .NET LTS version is confirmed and recorded (closes the ADR-0016 follow-up).
- [ ] `TimeZoneInfo` resolves the configured zone on the demonstration machine's operating system, and the offset is +1 hour before Sunday 25 October 2026 (CEST +2, CET +1 after) and +2 hours from Sunday 28 March 2027; any operating system dependency (for example ICU) is recorded.
- [ ] `dotnet list package --vulnerable` runs on the chosen baseline with no known vulnerable direct dependency.

_Notes:_ The zone name remains an assumption to confirm with Office Operations (F-01.02). The zone stays configuration, not code (ADR-0019).

### S-01.01.03: Confirm the timeline board and phone list UI approach

**Estimated Hours:** TBD

As a Software Engineer, I want to prototype a 15-minute-snapped timeline board and a per-room phone list in Razor Pages with a small amount of JavaScript so that the UI approach in ADR-0016 is confirmed feasible before the frontend features are built.

_Acceptance criteria:_

- [ ] A throwaway page renders rooms as rows and 08:00 to 20:00 as columns snapped to 15 minutes, and a click on free track selects a start time.
- [ ] The same data renders as a per-room vertical list at phone width with a "next free slot" line.
- [ ] The prototype is operable by keyboard and the findings note lists anything that needs more JavaScript than expected, with a recommendation.

_Notes:_ Design source: `.project/ui-designs/design-direction.md` (structural idea: the day timeline board) and screens S02-find-room, S02-find-room-mobile. If the finding recommends a different .NET UI style, ADR-0016 needs an amendment.
