## Description

Builds the three local harnesses (integration, API/contract, E2E) and the shared builders and helpers so that QA and developers can automate every acceptance criterion without inventing infrastructure per story.

## Scope Detail

- Integration test project: xUnit, temporary SQLite file per test class, one portable database fixture, `FakeTimeProvider`
- API/contract fixture over `WebApplicationFactory` with the reference seed and builders
- Playwright (.NET) fixture: random localhost port, fresh SQLite file and seed, time-relative setup helpers, desktop and phone viewports, traces and screenshots on failure
- Accessibility (axe) hook and browser installation scripts

## Technical Approach

Test projects created in F-02.01; fixtures per the test-strategy Local Development section; data builders create rooms, people and bookings per test with fictional data only.

## Stories

---

### S-10.01.01: Build the integration test fixture

**Estimated Hours:** TBD

As a QA Engineer, I want an integration fixture with a temporary SQLite file per test class and a fake clock so that real transactions and deterministic time are available to every test.

_Acceptance criteria:_

- [ ] Each test class gets a fresh temporary SQLite file created and removed by the fixture; the in-memory EF provider is not used.
- [ ] A single fixture class supplies the provider and connection; no test refers to SQLite-specific behaviour.
- [ ] A `FakeTimeProvider` starting at a fixed instant can be advanced by tests, and several connections to the same file are supported for concurrency tests.

_Notes:_ Test strategy v1.2, Test Levels and Portability rule.

---

### S-10.01.02: Build the API and contract fixture with builders

**Estimated Hours:** TBD

As a QA Engineer, I want a `WebApplicationFactory` fixture with the reference seed and data builders so that every HTTP behaviour can be asserted against a known starting point.

_Acceptance criteria:_

- [ ] The reference seed is exactly the specification's rooms (Focus 2, Team 6, Board 12 active; Old Room 4 inactive), one admin and several employees with fictional names and non-routable emails.
- [ ] Builders create rooms, people and bookings per test; each test adds only what it needs.
- [ ] A helper acts as a chosen person through the picker cookie so role boundaries can be asserted.

_Notes:_ Test strategy v1.2, Test Data Strategy.

---

### S-10.01.03: Build the E2E fixture and time-relative helpers

**Estimated Hours:** TBD

As a QA Engineer, I want a Playwright fixture that starts the app with fresh data so that E2E journeys run with no separate environment.

_Acceptance criteria:_

- [ ] The fixture starts the app on a random localhost port with a fresh SQLite file and the seed data, runs the journey and stops the app afterwards.
- [ ] Helpers place bookings relative to the real current time (for example starting in a few minutes for check-in, or already past the check-in window for the no-show outcome); no test waits for real minutes and no clock control exists.
- [ ] Journeys can run in a desktop viewport and a phone-size viewport; traces and screenshots on failure are written to a local folder.

_Notes:_ Test strategy v1.2, Clock section; SEC-11.

---

### S-10.01.04: Provide accessibility checks and run scripts

**Estimated Hours:** TBD

As a QA Engineer, I want axe checks and documented run commands so that accessibility and the running order are repeatable.

_Acceptance criteria:_

- [ ] An axe check can be invoked from the E2E fixture on the main screens.
- [ ] Scripts install the Playwright browsers once and run integration, API and E2E tests with documented `dotnet test` commands.
- [ ] The running order (build, unit, integration and API, dependency check, E2E) is written in the run guide input for F-11.02.

_Notes:_ NFR-016, NFR-018; test strategy v1.2, Running order.
