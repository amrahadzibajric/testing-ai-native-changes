# F-04.03: Role-based Authorisation and Privacy Enforcement

**Feature ID:** F-04.03
**EPIC:** [E-04: People and Identity](../epics/E-04-people-and-identity.md)
**Status:** Planned
**Phase:** Phase 1 — POC
**Sprint Range:** TBD (Phase 10)
**PD Estimate:** TBD (Phase 9)
**Last Updated:** 2026-09-29
**Status Reason:** Baseline WBS v1.0. Implements NFR-010 and NFR-012 as server-side rules.
**Surfaces:** Web, Phone browser
**Dependencies:** F-04.02, F-03.04 (403 page)
**ADR References:** ADR-0005, ADR-0015 (decision 4)
**Integration points:** None
**Open questions / risks:** Enforcement is against the selected identity and is not secure against a determined user (ADR-0005). The rules are real and tested; the limitation is demonstrated in E2E-014.

## Description

Makes the privacy and role rules true on the server: deny by default, admin-only pages, owner-or-admin checks on every booking handler, availability that never contains the booker, and a consistent refusal experience.

## Scope Detail

- Authorisation policies for Employee and Admin applied deny-by-default
- Owner-or-admin checks and owner-only check-in
- Separate read models so availability never selects owner data
- Consistent refusal messages

## Technical Approach

ASP.NET Core authorisation policies and page conventions; requirement handlers reading `ICurrentUser`; read-model types with no personal fields.

## Stories

---

### S-04.03.01: Apply deny-by-default authorisation policies

**Estimated Hours:** TBD

As a Software Engineer, I want every page and handler to require an explicit policy so that no new page is accidentally open.

_Acceptance criteria:_

- [ ] A page or handler without a policy is refused; the room, people, all-bookings, review and import pages require the Admin policy.
- [ ] An employee requesting any admin page or handler directly receives a refusal, not the page.
- [ ] The role used is always the one loaded from the database for the current request.

_Notes:_ NFR-010; E2E-009 and E2E-014 failure paths.

---

### S-04.03.02: Enforce ownership on every booking handler

**Estimated Hours:** TBD

As a Software Engineer, I want owner-or-admin checks so that an employee cannot read or change someone else's booking by guessing an id.

_Acceptance criteria:_

- [ ] Viewing, editing, cancelling or checking in to a booking not owned by the acting employee is refused and does not reveal whether the booking exists.
- [ ] Check-in is permitted only to the booking owner; an admin cannot check in on someone's behalf.
- [ ] Admins may edit and cancel any booking (subject to lifecycle rules in E-07).

_Notes:_ SEC-04; ADR-0015 decision 4; NFR-010.

---

### S-04.03.03: Separate privacy read models

**Estimated Hours:** TBD

As a Software Engineer, I want availability and personal listings built on separate read models so that the booker's identity cannot leak by accident.

_Acceptance criteria:_

- [ ] The availability read model has no owner, creator or other personal field, so it cannot return them.
- [ ] The employee's booking list can only be queried by the acting person's id.
- [ ] Only admin read models can query bookings across people.

_Notes:_ NFR-012; SEC-04. Used by F-06.03, F-06.06 and F-08.01.

---

### S-04.03.04: Provide a consistent refusal experience

**Estimated Hours:** TBD

As a Software Engineer, I want refused requests to show a clear message so that a user understands why an action is not allowed.

_Acceptance criteria:_

- [ ] A forbidden request shows the 403 page from F-03.04 stating that the action needs the admin role or ownership.
- [ ] The refusal does not include another person's data or internal identifiers.
- [ ] Refused state-changing requests change nothing and are logged without personal data.

_Notes:_ NFR-017 spirit; E2E-014.
