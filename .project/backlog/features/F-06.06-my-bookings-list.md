## Description

Shows a user their own upcoming and past bookings with status, including the label that distinguishes a booking cancelled by an admin from one they cancelled themselves.

## Scope Detail

- Own bookings only, upcoming first then past
- Status labels, late flag and cancelled-by-admin label
- Web and phone screens with the actions delivered by E-07 (edit, cancel, check in)

## Technical Approach

A per-person query on the employee read model (F-04.03), computing effective status so a lagging sweeper never shows a wrong status.

## Stories

---

### S-06.06.01: List my upcoming and past bookings

**Estimated Hours:** TBD

As a Software Engineer, I want My bookings to list only the acting person's bookings so that employees see their own bookings and nobody else's.

_Acceptance criteria:_

- [ ] The list shows the acting person's bookings with room, date, time, attendees and status; upcoming bookings appear first, then past ones.
- [ ] No other person's booking can be listed or opened.
- [ ] An empty list shows the empty state with a link to Find a room.

_Notes:_ NFR-012; E2E-009 step 4, E2E-014 step 2.

---

### S-06.06.02: Present status, late flag and cancellation origin

**Estimated Hours:** TBD

As a Software Engineer, I want clear status labels so that a booker can tell an admin cancellation from their own and see the effective status.

_Acceptance criteria:_

- [ ] A booking cancelled because a room or person was deactivated, or cancelled directly by an admin, is labelled "Cancelled by admin"; a booking the owner cancelled shows Cancelled and, if applicable, the late flag.
- [ ] Effective status is shown: a Confirmed booking past start plus 15 minutes reads No-show even before the sweeper persists it.
- [ ] Status uses the shared vocabulary and text labels.

_Notes:_ LC-12; AO-05; E2E-010 step 4.

---

### S-06.06.03: Build My bookings for web and phone

**Estimated Hours:** TBD

As a Software Engineer, I want the My bookings screens so that users can review bookings and reach actions on desktop and phone.

_Acceptance criteria:_

- [ ] The web screen is a list with per-booking actions (edit, cancel, check in) enabled only when the lifecycle rules allow; the phone screen follows S02-my-bookings-mobile including the check-in open state.
- [ ] Actions that are not allowed (for example after start) are not offered and explain why on request.
- [ ] Both screens meet the accessibility baseline and phone touch-target size.

_Notes:_ Actions delivered by F-07.01, F-07.02 and F-07.03.
