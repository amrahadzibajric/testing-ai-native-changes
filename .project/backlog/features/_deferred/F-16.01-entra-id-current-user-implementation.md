## Description

Adds an OpenID Connect implementation of `ICurrentUser` for the company tenant, linking accounts to existing people first by verified email and then by the immutable object identifier.

## Scope Detail

- OIDC single-tenant sign-in implementing `ICurrentUser`
- First sign-in link by verified email; store object id and tenant; later match by object id
- Roles remain in the application database

## Technical Approach

Microsoft.Identity.Web or equivalent; person external identity fields already present in the model; no rule changes because all rules read `ICurrentUser`.

## Stories

---

### S-16.01.01: Implement the OIDC `ICurrentUser`

**Estimated Hours:** TBD

As a Software Engineer, I want an Entra-based `ICurrentUser` so that users sign in with company accounts and rules are unchanged.

_Acceptance criteria:_

- [ ] After sign-in the acting person and role come from the database through `ICurrentUser`.
- [ ] Tokens are validated for a single tenant; a token from another tenant is refused.
- [ ] No module changes are needed beyond configuration.

_Notes:_ ADR-0022 Option A.

---

### S-16.01.02: Link accounts safely

**Estimated Hours:** TBD

As a Software Engineer, I want accounts linked once on a verified email and then bound to the object id so that an unrelated account cannot take over a person record.

_Acceptance criteria:_

- [ ] The first sign-in matches the verified email claim ignoring case to an existing active person and stores the object id and tenant id.
- [ ] Later sign-ins match on the object id; a different account presenting the same email is refused.
- [ ] A sign-in with no matching person is refused with a clear message.

_Notes:_ SEC-07; unique index on the object id.

---

### S-16.01.03: Keep roles in the database and preserve audit

**Estimated Hours:** TBD

As a Software Engineer, I want roles and the audit trail unchanged so that the switch adds no migration.

_Acceptance criteria:_

- [ ] Role changes by admins take effect on the next request.
- [ ] Audit events keep recording the acting person and, where present, the gate identity.
- [ ] Deactivated people cannot sign in.

_Notes:_ ADR-0006: no data migration required.
