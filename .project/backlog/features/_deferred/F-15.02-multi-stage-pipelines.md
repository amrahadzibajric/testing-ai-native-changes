## Description

Defines the YAML pipelines: PR validation, merge to main with deployment to test and gate-aware E2E smoke tests, and a manually approved production stage.

## Scope Detail

- PR validation: restore, build, unit, integration and API tests (SQL Server containers), dependency scan
- Merge to main: publish, deploy Bicep and app to test, gate reachability probe, E2E smoke set
- Production: manual approval outside office hours, verifying no clock control and gate redirect
- Test access to the gate via service principal token

## Technical Approach

Multi-stage YAML in the repository; environments with approvals; the same commands used locally in the POC become stages.

## Stories

---

### S-15.02.01: Implement PR validation

**Estimated Hours:** TBD

As a Software Engineer, I want a PR pipeline so that every change is built and tested before merge.

_Acceptance criteria:_

- [ ] Restore, build, unit, integration and API tests (Testcontainers SQL Server) and the dependency vulnerability scan run on every pull request and gate the merge.
- [ ] The stage finishes within its timeout (about 10 minutes).
- [ ] Test results are published to Azure DevOps.

_Notes:_ Test strategy v1.2 target pipeline stages.

---

### S-15.02.02: Implement merge-to-main deployment to test

**Estimated Hours:** TBD

As a Software Engineer, I want merges deployed to the test environment with smoke tests so that hosted defects surface early.

_Acceptance criteria:_

- [ ] A merge publishes an artifact and deploys Bicep and the application to test, then runs the gate reachability probe and the E2E smoke set (one journey per module).
- [ ] The test environment resets to seed data at the start of each run.
- [ ] A failing stage stops the pipeline.

_Notes:_ Test strategy v1.2.

---

### S-15.02.03: Implement production deployment with approval and checks

**Estimated Hours:** TBD

As a Software Engineer, I want a controlled production stage so that only tested artifacts reach production.

_Acceptance criteria:_

- [ ] Production requires manual approval on an Azure DevOps environment and deploys outside office hours.
- [ ] The stage verifies that no clock-control endpoint exists in the build and that unauthenticated requests are redirected to sign-in.
- [ ] The same tested artifact is promoted, not rebuilt.

_Notes:_ SEC-11, SEC-12.

---

### S-15.02.04: Give automated tests access through the gate

**Estimated Hours:** TBD

As a Software Engineer, I want automated tests to obtain a token for the gate so that hosted E2E, k6 and ZAP can run without brittle interactive sign-in.

_Acceptance criteria:_

- [ ] A service principal token is obtained (client credentials or workload identity) and sent as a bearer token by Playwright's API context, k6 and ZAP; the gate app registration accepts that audience.
- [ ] The test environment stays gated; leaving it ungated is not used.
- [ ] If client IT refuses, the documented fallback test user is used.

_Notes:_ Test strategy v1.2.
