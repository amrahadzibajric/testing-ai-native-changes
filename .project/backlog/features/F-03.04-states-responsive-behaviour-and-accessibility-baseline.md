## Description

Provides the empty, loading and error state patterns, the responsive behaviour for phone and desktop browsers, an accessibility baseline (keyboard, contrast, semantics, live regions) and friendly error pages.

## Scope Detail

- Empty, loading and error patterns: one line of plain language plus a next action
- Responsive behaviour for latest two versions of Chrome, Edge, Safari and Firefox on desktop; Chrome and Safari on phones
- Accessibility baseline aiming at WCAG 2.1 AA
- Error pages for 403, 404 and 500

## Technical Approach

Reusable partials and CSS breakpoints; semantic HTML; focus management helpers shared with drawer and sheet.

## Stories

---

### S-03.04.01: Provide empty, loading and error state patterns

**Estimated Hours:** TBD

As a Software Engineer, I want shared state patterns so that every list and page handles "nothing here", "loading" and "failed" the same way.

_Acceptance criteria:_

- [ ] An empty state shows one plain-language line and one next action, with no illustration.
- [ ] A loading state is shown for operations that take noticeable time (search, import) and does not shift layout.
- [ ] An error state shows a readable message and a retry or back action, never a stack trace.

_Notes:_ Design direction (no decorative illustration).

---

### S-03.04.02: Deliver responsive behaviour for desktop and phone browsers

**Estimated Hours:** TBD

As a Software Engineer, I want pages that adapt from desktop to phone width so that availability, booking and especially check-in work in the supported browsers.

_Acceptance criteria:_

- [ ] Layouts adapt at the phone breakpoint: tab bar replaces navbar, tables become lists or scroll horizontally, drawers become bottom sheets.
- [ ] The main screens render and operate in the latest two versions of Chrome, Edge, Safari and Firefox on desktop, and in Chrome and Safari on phones.
- [ ] No horizontal page scroll occurs at 360 px width on the main screens.

_Notes:_ NFR-016; phone behaviour is demonstrated with a narrow window or device emulation.

---

### S-03.04.03: Deliver the accessibility baseline

**Estimated Hours:** TBD

As a Software Engineer, I want semantic HTML, keyboard operation and sufficient contrast so that the POC reaches the WCAG 2.1 AA design aim.

_Acceptance criteria:_

- [ ] Every interactive control is reachable and operable by keyboard, including the timeline board slots, drawer, sheet and confirm modal, with visible focus.
- [ ] Text and status colours meet AA contrast; meaning is never conveyed by colour alone.
- [ ] Messages and toasts use live regions; a skip-to-content link exists; form fields have associated labels.

_Notes:_ NFR-018; automated checks are derived by QA in E-10.

---

### S-03.04.04: Provide friendly error pages

**Estimated Hours:** TBD

As a Software Engineer, I want 403, 404 and 500 pages in the design language so that refusals and failures are understandable.

_Acceptance criteria:_

- [ ] A forbidden request shows a clear message stating that the action needs the admin role and a link back to a permitted page.
- [ ] An unknown address shows a not-found page; an unexpected error shows a generic message with no internals.
- [ ] All three use the shell, are keyboard accessible and meet AA contrast.

_Notes:_ Gap: no canvas artboard exists for these pages.
