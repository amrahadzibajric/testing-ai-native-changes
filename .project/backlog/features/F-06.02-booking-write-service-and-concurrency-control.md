## Description

Builds the one code path that creates or moves a booking. It takes the SQLite write lock at the start of the transaction, re-checks every rule against current data, writes the booking and audit event and commits, so that two simultaneous requests can never both succeed for the same slot.

## Scope Detail

- Single booking-write service used by create, edit, remainder rebooking and import
- Immediate SQLite write transaction with rules re-checked inside it
- WAL mode and busy timeout so a waiting writer waits rather than failing
- Optimistic concurrency token for edits
- A clean seam for the later per-room lock on Azure SQL

## Technical Approach

A scoped write service opening an immediate transaction (API confirmed in S-01.01.01), invoking the rules engine against fresh reads, persisting and auditing in the same transaction, and rolling back on refusal.

## Stories

---

### S-06.02.01: Provide the single booking-write service

**Estimated Hours:** TBD

As a Software Engineer, I want one service to be the only way a booking is created or moved so that every path enforces the same guarantees.

_Acceptance criteria:_

- [ ] Manual booking, edit, remainder rebooking and import call the same service.
- [ ] No other code creates or moves a booking (enforced by S-02.01.04).
- [ ] The service exposes a provider-neutral interface so the SQL Server per-room lock can be substituted later without changing callers.

_Notes:_ ADR-0020 decision; IM-03.

---

### S-06.02.02: Write inside an immediate transaction with rules re-checked

**Estimated Hours:** TBD

As a Software Engineer, I want the write lock taken at the start of the transaction so that two requests cannot both read before either writes.

_Acceptance criteria:_

- [ ] The transaction acquires the write lock before the overlap and limit checks, re-checks every rule against current data, writes the booking and the audit event and commits.
- [ ] A refused request rolls back and leaves no booking and no audit event.
- [ ] A deferred transaction is never used for booking writes.

_Notes:_ ADR-0025 rule 5; key flow 1 in arch v1.2.

---

### S-06.02.03: Guarantee a single winner under concurrency

**Estimated Hours:** TBD

As a Software Engineer, I want concurrent identical requests to produce exactly one booking so that a room is never double booked.

_Acceptance criteria:_

- [ ] N simultaneous identical requests for one slot result in exactly one success; the others are refused with the named rule "room already booked".
- [ ] A manual booking during an import cannot produce an overlap or exceed a person's 3-booking limit.
- [ ] A waiting request waits for the lock up to the busy timeout and does not fail with a database-locked error.

_Notes:_ NFR-005; E2E-001 failure path. WAL and busy timeout values come from S-01.01.01.

---

### S-06.02.04: Protect edits with an optimistic concurrency token

**Estimated Hours:** TBD

As a Software Engineer, I want an application-managed concurrency token so that two simultaneous edits of one booking cannot silently overwrite each other.

_Acceptance criteria:_

- [ ] Every update replaces the booking's token; an update carrying a stale token is refused with a message asking the user to reload.
- [ ] Two simultaneous edits of the same booking result in one success and one refusal.
- [ ] The token is a mapped concurrency token, not a database-generated value.

_Notes:_ Data model: `row_version` application-managed on SQLite.
