## Description

Provides the append-only audit recorder that writes an event in the same transaction as the change it describes. It records the acting person or the system, whether an admin acted, the action, the logical target and compact before/after details, so that late-cancellation and cancelled-by-admin records are trustworthy.

## Scope Detail

- Append-only audit events written in the change transaction
- Actor capture: person or system, admin flag; gate fields present but empty
- Compact JSON details without personal data beyond ids
- Action list from the data model

## Technical Approach

An audit recorder service enlisted in the caller's database transaction. Event shape follows `audit.md`; details are a small JSON document.

## Stories

---

### S-02.04.01: Record audit events in the change transaction

**Estimated Hours:** TBD

As a Software Engineer, I want an audit recorder that writes in the same transaction as the change so that no state change can exist without its audit record.

_Acceptance criteria:_

- [ ] Every action in the data-model action list can be recorded with time from the office clock, action, target type and target id.
- [ ] If the change transaction rolls back, no audit event remains.
- [ ] The application has no update or delete path for audit events.

_Notes:_ NFR-020.

---

### S-02.04.02: Capture the acting person, system actor and admin flag

**Estimated Hours:** TBD

As a Software Engineer, I want the actor captured consistently so that admin actions and system actions can be told apart.

_Acceptance criteria:_

- [ ] Events by a person record the acting person id and whether that person held the Admin role at that moment.
- [ ] Sweeper and bootstrap events record actor kind System with no acting person.
- [ ] The gate sign-in name, gate object id and mismatch fields exist and are empty in the POC.

_Notes:_ The acting person is the picked identity, not proof of who is at the keyboard (ADR-0005).

---

### S-02.04.03: Keep audit details compact and free of personal data

**Estimated Hours:** TBD

As a Software Engineer, I want audit details limited to compact before/after facts and ids so that the trail does not leak personal data.

_Acceptance criteria:_

- [ ] Details hold compact JSON such as old and new start, room and attendees, cancellation origin, or import counts.
- [ ] Details never contain request bodies or other people's full email addresses; people are referenced by id.
- [ ] Cancellation events carry the cancellation origin so late and admin cancellations can be traced.

_Notes:_ SEC-09; AO-03.
