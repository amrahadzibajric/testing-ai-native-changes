## Description

Computes the five-working-day import window and validates each row: field formats, room and person matching, every booking rule, ordering per person and overlap between rows. Every broken rule is reported by name.

## Scope Detail

- Window: go-live date if a weekday, else the following Monday; 5 working days Monday to Friday; no holiday calendar
- Field formats and reference matching (exact room name, case-insensitive email, active room and person)
- All booking rules through the shared rules engine, reporting every failed rule
- Ordering by date and time (ties by file order), 3-booking limit, overlap between rows

## Technical Approach

A validation pipeline that parses each row to a candidate booking, calls the rules engine in collect-all mode, then applies ordering-dependent rules with the current database state and previously accepted rows.

## Stories

---

### S-09.02.01: Compute the import window

**Estimated Hours:** TBD

As a Software Engineer, I want the window computed from the go-live date so that only the intended five working days are imported.

_Acceptance criteria:_

- [ ] A weekday go-live date starts the window that day; a Saturday or Sunday go-live starts it on the following Monday; the window spans five working days Monday to Friday with no holiday calendar.
- [ ] The go-live date and window start and end dates are stored on the ImportRun as office-local dates.
- [ ] Rows dated outside the window are rejected with OutsideWindow, and a weekend date with NotWorkingDay.

_Notes:_ IM-01; ADR-0014 rule 4; ADR-0015 decision 5.

---

### S-09.02.02: Validate field formats and match rooms and people

**Estimated Hours:** TBD

As a Software Engineer, I want each field validated and matched so that only rows that refer to real rooms and people are imported.

_Acceptance criteria:_

- [ ] `date` must be `YYYY-MM-DD`, `start` and `end` `HH:MM`, `attendees` a whole number; anything else is rejected with MissingOrBadFormat.
- [ ] `room` must match an active room name exactly (ignoring case); an unknown room is RoomUnknown and an inactive room such as Old Room is RoomInactive.
- [ ] `person_email` must match an existing person ignoring case; unknown is PersonUnknown and inactive is PersonInactive.

_Notes:_ IM-02; ADR-0011; RM-02, NFR-023.

---

### S-09.02.03: Apply every booking rule through the shared rules engine

**Estimated Hours:** TBD

As a Software Engineer, I want the import to use the same rules as manual booking so that imported bookings are valid by construction.

_Acceptance criteria:_

- [ ] Grid, office hours, duration, capacity, attendees and no-past rules are applied per row; the row's reasons list every rule it breaks, using the same rule names and messages as manual refusals.
- [ ] A row is imported exactly as given or rejected; times, rooms and attendees are never adjusted.
- [ ] Rows that would start in the past at import time are rejected with InPast.

_Notes:_ IM-03, IM-06, IM-07; NFR-017.

---

### S-09.02.04: Order rows and apply the limit and overlap rules

**Estimated Hours:** TBD

As a Software Engineer, I want deterministic ordering so that the limit and overlap outcomes are predictable and never chosen on business grounds.

_Acceptance criteria:_

- [ ] Rows are processed in date and time order, ties by file order; per person the first three upcoming bookings (including bookings already in the tool) are accepted and later rows are rejected with LimitExceeded.
- [ ] Where two rows overlap in one room, the row processed first is accepted and the later row is rejected with Overlap.
- [ ] A person with five rows in the window gets the first three imported and rows four and five rejected.

_Notes:_ IM-04, IM-05; ADR-0014 rule 2; E2E-013 failure path.
