## Description

Implements the full conceptual data model in EF Core against SQLite, with provider-neutral entities, the SQLite-specific mapping isolated in one configuration point, indexes, migrations and a guard that keeps provider-specific types out of the model. After this feature every later feature reads and writes real tables.

## Scope Detail

- Entities: Person, Room, Booking, AuditEvent, ImportRun, ImportReportRow with the data-model constraints
- SQLite mapping: WAL, busy timeout, `NOCASE` unique indexes, UTC `DateTime` as ISO-8601 text, GUIDs as text, application-managed `row_version`
- Indexes named in the data model
- Initial migration applied at startup; reset by deleting the file
- Guard against `DateTimeOffset` and provider-specific types

## Technical Approach

EF Core code-first with one persistence configuration point holding all provider differences. Migrations are SQLite-specific; a new baseline is generated for Azure SQL later (E-13).

## Stories

---

### S-02.02.01: Implement all entities and mappings

**Estimated Hours:** TBD

As a Software Engineer, I want every entity from the data model mapped in EF Core so that all later features share one persisted model.

_Acceptance criteria:_

- [ ] Person, Room, Booking, AuditEvent, ImportRun and ImportReportRow exist with the attributes, enumerations (stored as strings) and relationships in `.project/data-model/`.
- [ ] Status-dependent rules are enforced: `checked_in_at` for CheckedIn and Done, `no_show_at` for NoShow, cancellation fields required only when Cancelled, late flag only with OwnerCancelled, end after start, attendees at least 1.
- [ ] No physical deletion path exists for people, rooms, bookings, audit events or import runs, except the import report purge defined in F-09.04.

_Notes:_ NFR-021 (retain history). The external identity fields on Person and the gate fields on AuditEvent exist and stay empty in the POC.

---

### S-02.02.02: Configure SQLite behaviour in one place

**Estimated Hours:** TBD

As a Software Engineer, I want all provider differences in a single persistence configuration point so that moving to Azure SQL is a contained change.

_Acceptance criteria:_

- [ ] The database runs in WAL mode with the busy timeout recorded by S-01.01.01.
- [ ] Unique indexes on person email and room name use `NOCASE`, so a duplicate differing only in case is refused.
- [ ] All instants are UTC `DateTime` stored as ISO-8601 text through a converter that enforces `Kind = Utc`; date-only fields are ISO date text; GUIDs are text.
- [ ] `row_version` is an application-managed token replaced on every update and configured as a concurrency token.

_Notes:_ NFR-023; ADR-0025 rules 2 to 4. Accented characters are not asserted in the POC.

---

### S-02.02.03: Add the indexes the queries need

**Estimated Hours:** TBD

As a Software Engineer, I want the data model's indexes so that availability, my-bookings, sweeper and review queries stay fast at a few thousand bookings.

_Acceptance criteria:_

- [ ] Indexes exist on (room, start), (owner, status, start), (status, start), audit (target type, target id, time) and audit (time), and on the review columns.
- [ ] A query-plan check shows the availability query and the sweeper query use an index rather than a table scan on 5,000 seeded bookings.
- [ ] The migration contains no index type specific to another provider.

_Notes:_ NFR-002, NFR-003.

---

### S-02.02.04: Provide migrations and the database lifecycle

**Estimated Hours:** TBD

As a Software Engineer, I want an initial migration applied at startup and a simple reset so that the POC starts clean on any machine.

_Acceptance criteria:_

- [ ] On first start the SQLite file is created at the configured location and the initial migration is applied.
- [ ] Deleting the file and restarting returns the application to the clean seeded state.
- [ ] Starting against an already migrated file applies nothing and does not fail.

_Notes:_ Migrations are generated per provider (ADR-0025 rule 7).

---

### S-02.02.05: Guard provider neutrality

**Estimated Hours:** TBD

As a Software Engineer, I want an automated guard against provider-specific constructs so that the later Azure SQL switch stays a provider and migration change.

_Acceptance criteria:_

- [ ] The build or test run fails if `DateTimeOffset` or a provider-specific column type or raw SQL appears in the domain or model.
- [ ] The guard message names the offending property or file.
- [ ] Provider differences appear only in the persistence configuration point.

_Notes:_ Follow-up in ADR-0025 and the data model open items.
