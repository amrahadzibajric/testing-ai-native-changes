## Description

Delivers the `ICurrentUser` seam with its pick-a-user implementation, the entry page that lists active people only, the always-visible identity block with Switch user, and safe handling of stale or tampered identities.

## Scope Detail

- `ICurrentUser` interface as the only place identity is established
- Signed, encrypted cookie holding only the person id; role and person loaded from the database each request
- Pick-a-user page for web and phone with an empty state
- Header shows acting-as person, role and Switch user; picker switch audited
- Stale, deactivated and tampered identity handling

## Technical Approach

Cookie authentication scheme or equivalent over ASP.NET Core data protection; a scoped service resolving the person by id per request; all authorisation reads from `ICurrentUser`.

## Stories

---

### S-04.02.01: Implement `ICurrentUser` with the picker implementation

**Estimated Hours:** TBD

As a Software Engineer, I want a single current-user abstraction so that every rule reads the acting person and role from one place and Microsoft sign-in can replace the picker later.

_Acceptance criteria:_

- [ ] `ICurrentUser` exposes the acting person id, name, email, role and active flag, loaded from the database on every request.
- [ ] The picker cookie is signed and encrypted and holds only the person id; a role or id supplied by the browser in any other form is never trusted.
- [ ] No module reads identity except through `ICurrentUser` (enforced by S-02.01.04).

_Notes:_ ADR-0022 Option A; SEC-02; PI-08.

---

### S-04.02.02: Build the pick-a-user page

**Estimated Hours:** TBD

As a Software Engineer, I want a start page listing active people so that a presenter or employee can choose who to act as.

_Acceptance criteria:_

- [ ] The page lists active people with name and role only; inactive people are not listed.
- [ ] Choosing a person stores the cookie and opens the role-appropriate landing page (Find a room).
- [ ] When no active person exists an empty state explains the situation; the layout matches S01 on web and phone.

_Notes:_ ADR-0014 rule 5; E2E-001 step 1; E2E-014.

---

### S-04.02.03: Show the acting user and support Switch user

**Estimated Hours:** TBD

As a Software Engineer, I want the header to show who the presenter is acting as and allow switching so that employee and admin views can be demonstrated.

_Acceptance criteria:_

- [ ] Every page shows the acting person's name and role with a Switch user link returning to the picker.
- [ ] Each switch records a PickerSwitch audit event with the person acted as.
- [ ] Switching from an employee to an admin immediately exposes admin destinations (E2E-014).

_Notes:_ M-04 capability 7; visible symptom of the pilot limitation.

---

### S-04.02.04: Handle stale identities

**Estimated Hours:** TBD

As a Software Engineer, I want the server to re-evaluate the identity on every request so that a deactivated or changed person cannot keep acting on old assumptions.

_Acceptance criteria:_

- [ ] If the cookie's person has been deactivated, the next request redirects to the picker with a message.
- [ ] If the person's role changed, the new role applies on the very next request.
- [ ] A cookie referencing a person id that does not exist is treated as no identity.

_Notes:_ ADR-0014 (deactivation), SEC-02.

---

### S-04.02.05: Harden the picker cookie

**Estimated Hours:** TBD

As a Software Engineer, I want the cookie hardened so that a user cannot forge or replay another identity by editing it.

_Acceptance criteria:_

- [ ] Editing the cookie value results in no identity and a redirect to the picker.
- [ ] The cookie is HttpOnly and SameSite; Secure is set whenever HTTPS is used.
- [ ] A cookie signed with a discarded key ring is rejected.

_Notes:_ SEC-02.
